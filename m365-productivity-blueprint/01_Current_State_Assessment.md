|---|---|---|---|---|---|---|---|---|

## 5. 근본 진단: "SCM 담당자가 사람 미들웨어(Human Middleware)로 쓰이고 있다"

분해 결과에서 공통 패턴이 하나 보인다. **정보가 시스템이 아니라 사람을 거쳐 흐른다.**
- 요청은 메일함에, 결정은 회의 참석자 기억에, 데이터는 사람의 복사·붙여넣기에, 진행 상황은 '물어봐야 아는' 상태에 있다.
- 그래서 SCM 담당자의 시간 중 큰 부분이 **판단이 아니라 전달·확인·재요청**에 쓰인다(Lean 관점: 운반·대기·재작업·과잉처리 낭비).

| Lean 낭비 | SCM 사무 업무에서의 모습 | 근본 원인 | 대응 원칙 |
|---|---|---|---|
| 운반 | 같은 파일을 메일로 주고받기, 첨부 재전달 | 단일 원본 없음 | O26 링크 공유·O04 단일 원본 |
| 대기 | 결정 기다림, 공장 회신 기다림 | 결정 요청이 보이지 않음 | O15 결정 대기열 |
| 재작업 | 양식 오류 재요청, 버전 혼선 | 입력 시점 검증 없음 | O04 데이터 계약(입력 시점 자동 검증) |
| 과잉처리 | 매주 같은 표 다시 만들기, 아무도 안 읽는 주간보고 | 보고가 '산출물'이 됨 | O17 보고 제거, O14 회의 비동기화 |
| 동작 | 메일·채팅·파일 사이를 오가며 상태 확인 | 상태 정보 분산 | O01 아침 브리핑(한 장) |
| 결함 | 수치 불일치, 결정 미이행 | 추적 체계 없음 | O03 결정–액션 레지스터 |
| 재고(정보) | 처리 안 된 요청이 메일함에 쌓임 | 요청이 비구조화 | O05 요청 허브 |

**설계 원칙(이후 전 문서 공통):** ① 정보는 발생 지점에서 한 번만 구조화해 입력한다 ② 상태는 묻지 않고 본다 ③ 정상은 침묵하고 예외만 알린다 ④ 사람은 판단·약속·승인만 한다.

### 과거 'Power Automate 연결 인증 오류'의 흔한 원인 (점검 순서)
1. 흐름을 만든 계정과 연결(Connection)을 만든 계정이 다름(다른 사람이 만든 흐름을 공동 소유자로 받은 경우) → 흐름 편집 화면에서 각 액션의 **연결 참조**를 내 연결로 교체
2. 비밀번호 변경·MFA 재등록·조건부 액세스 정책으로 연결 토큰 만료 → **연결 → 연결 수정(Fix connection)**
3. DLP 정책이 커넥터 조합(예: 업무 데이터 그룹 ↔ 비업무 그룹)을 막음 → 흐름 저장 시 경고, 관리자 정책 확인 필요(우회 금지)
4. 공유받은 흐름의 '실행 전용 사용자(Run-only users)' 설정에서 연결 제공 방식이 '실행자 제공'으로 되어 있음
5. 대상 SharePoint 사이트·목록에 실행 계정 권한 없음 → 사이트 권한 확인

→ 이 원인들은 **개인 계정 소유 흐름**에서 반복된다. 팀 확산 시에는 흐름 공동 소유자 2명 이상 + 팀 사이트 저장 + 연결 목록 문서화를 규칙으로 둔다(05 문서 거버넌스).
